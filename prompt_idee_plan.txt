# ROOTS / VILLAGE

## Technical Product & Implementation Blueprint

**Product vision**

ROOTS / Village is a privacy-first family diaspora platform helping parents:

1. discover compatible families nearby;
2. build trusted local micro-communities called Villages;
3. organize real-world cultural experiences;
4. transmit language, culture and family history to their children;
5. preserve those memories over many years through a private Roots Passport.

The platform is not designed as another social network.

Its product loop is:

**Discover → Connect → Build a Village → Meet → Experience Culture → Preserve Memory → Repeat**

The initial launch market is:

**Cameroonian families living in Germany**

but the architecture must support multiple countries, cultures, languages and diaspora communities from day one.

---

# 1. PRODUCT PRINCIPLES

Every implementation decision must respect these principles.

### 1.1 Children are not social-network users

Children do not create accounts.

Every child profile belongs to one or more authorized guardians.

Children:

* cannot be searchable by strangers;
* cannot be directly messaged;
* cannot expose exact location;
* cannot have public contact information;
* cannot have public profiles indexed by search engines.

---

### 1.2 Approximate location by default

Never display a family's exact home coordinates.

The platform may internally use coordinates to calculate distance, but other users should only see values such as:

> 12 km away

or:

> Ingolstadt area

Public/client-visible location should use deliberately reduced precision.

---

### 1.3 Real-world interaction over endless feeds

ROOTS should not become Facebook for diaspora families.

Therefore avoid:

* infinite public feeds;
* follower counts;
* popularity scores;
* public child profiles;
* vanity metrics.

Prioritize:

* matching;
* Villages;
* activities;
* cultural missions;
* family memories.

---

### 1.4 Privacy before growth

The platform deals with families and children.

Default visibility must always be conservative.

Users explicitly opt into additional visibility.

# 12. GEOLOCATION

Use PostGIS.

Internal location may store approximate user-selected coordinates.

Never force precise GPS.

On onboarding:

1. ask city/postcode;
2. geocode;
3. store approximate coordinates;
4. optionally allow device location with explicit consent.

Distance calculation:

```sql
ST_DWithin(...)
ST_Distance(...)
```

Create a secure database RPC such as:

```text
discover_families(
    requester_family_id,
    radius_km,
    filters
)
```

RPC returns:

```text
family_id
display_city
distance_bucket
match_score
child_age_ranges
shared_cultures
shared_languages
shared_interests
```

It must NOT return:

```text
latitude
longitude
street
postcode
private contact info
child full names
```

# 14. MATCHING ENGINE V1

Do not begin with AI.

Use deterministic weighted scoring.

Example:

```text
distance               25%
children age overlap   20%
cultural overlap       15%
language overlap       10%
shared interests       15%
availability overlap   10%
stated preferences      5%
```

Total:

```text
0–100
```

Possible formula:

```text
score =
distance_score * 0.25 +
child_age_score * 0.20 +
culture_score * 0.15 +
language_score * 0.10 +
interest_score * 0.15 +
availability_score * 0.10 +
preference_score * 0.05
```

Return explanations.

Example:

> 91% compatibility

Because:

```text
Children around same age
12 km away
Both families speak French and German
Interested in cultural activities
Usually available Saturday afternoon
```

Never expose internal sensitive information to explain scoring.

---

# 34. ROW LEVEL SECURITY

RLS must be enabled on every exposed user-data table.

Examples.

A family member can edit their family:

```sql
family_id IN (
  SELECT family_id
  FROM family_members
  WHERE profile_id = current_profile_id()
)
```

A parent can access their children.

Village members can access village-only data.

A child Roots Passport can only be accessed by authorized guardians unless explicitly shared.

Blocked families must disappear from discovery.

# FINAL PRODUCT ARCHITECTURE

ROOTS should ultimately consist of five interconnected engines:

## 1. Discovery Engine

> Who are the families around us?

Geo + compatibility.

## 2. Village Engine

> How do we create meaningful relationships?

Micro-communities + activities + communication.

## 3. Culture Engine

> What do we want our children to discover?

Languages + missions + traditions + experiences.

## 4. Memory Engine

> What do we preserve for them?

Roots Passport + photos + stories + grandparents.

## 5. Trust Engine

> How do families interact safely?

Privacy + consent + verification + moderation + permissions.

The technological moat is therefore not one AI feature.

It is the accumulated graph connecting:

```text
Families
        ↕
Cultures
        ↕
Languages
        ↕
Local communities
        ↕
Events
        ↕
Experiences
        ↕
Family memories
```

That graph becomes increasingly valuable as the family continues using ROOTS over years.

The product should therefore be engineered as a **long-term family cultural infrastructure**, not as a disposable social application.
